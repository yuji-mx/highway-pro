# ADR-0014 標高タイルの事前一括取得と一時的な失敗の扱い

- 状況：大規模地域（California など）の build で、metrics 段の「ランプ解析」が極端に遅く、3DEP ImageServer から 504 が
  返ることがあった。原因は (1) 標高タイルを要素の解析ループの中で 1 枚ずつ逐次取得していたこと（並列化なし）、
  (2) 3DEP の 1 要求が 1〜11 秒かかること、(3) 5xx は既定 180 秒のタイムアウト × 5 回（指数バックオフ込みで最長約 15 分）
  再試行した後に例外となり、build 全体が中断していたこと。
- 決定：
  1. **事前一括取得**：metrics 段の最初に、解析と同じ内部刻み（`analysis.elevation.internal_step_m`）で全要素の点を作り、
     必要なタイルを列挙してキャッシュにないものだけを並列取得する（`DemSampler.prefetch`）。上位の DEM で得られない
     タイル（404・失敗）にある点だけを下位の DEM（Copernicus など）の事前取得に回す。進捗は metrics 段の前半に
     「標高タイル取得 n/N（失敗 k）」として表示する。事前取得は最適化であり、取りこぼしは従来どおり標本化時に取得される。
  2. **3DEP のまとめ取得**：`block_tiles`（既定 4）× `block_tiles` の区画ごとに、必要なタイルを囲む最小の長方形を
     1 要求で取得し、タイルごとに分けてキャッシュする（キャッシュ形式は従来と同じ）。実測で 16 タイルが約 10 秒
     （1 タイル要求は 1〜11 秒）。まとめ取得と単独取得の画素値の差は最大 0.00012 m（浮動小数点の丸め）。
  3. **一時的な失敗**：再試行後も 5xx・タイムアウトのタイルは、その実行中は再要求せず下位の DEM で補完して build を続ける。
     404 と違いキャッシュに記録しないため、次回の build（`--from-step metrics`）で再取得される。件数はログの
     `dem_tile_failed` / `dem_prefetch` と、`dem_sources`（要素ごとの使用 DEM）に残る。
  4. **ホスト別の設定**：`http.rate_limits.<host>` に `timeout_s`・`max_retries` を追加（3DEP は 120 秒・3 回）。
     429/503 の `Retry-After` を `http.retry_after_cap_s` を上限に尊重する。同時接続数は従来どおりホスト別の
     `max_concurrency`（3DEP は 2、地理院は 4）で制限し、公開 API への負荷は増やさない。
- 結果：`docs/validation/dem-fetch.md`。
- 却下した案：3DEP 1/3 秒角の 1° GeoTIFF（S3 の COG）を使う案は、州全域で数十 GB になり、部分読み出しには
  HTTP の範囲要求を `ingest/http.py` に実装する必要があるため今回は見送った（将来の選択肢）。
