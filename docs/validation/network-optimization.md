# 大規模地域の処理高速化（2026-11-12）

## 背景

California の build がランプ抽出（進捗 30 %）で 2 時間以上進まなかった（提案者の報告）。原因は、施設のリンク連結成分ごとに
州全体の辺を 2 回ずつ走査していたこと（施設数 × 成分数 × 全辺数）。同様の「全件の繰り返し走査」がほかの段にもあったため、
あわせて削減した。数値解析の設定・標高解像度・通信の並列度は変えていない。**出力はすべて変更前とビット単位で同一**（下記）。

## 変更点

| 工程 | 改善 | 出典 |
| --- | --- | --- |
| OSM 読込 | iterrows とセル単位の更新を itertuples と列単位の更新に置換 | 提案パッチ |
| 本線方位（米国） | 番号のない路線の軸を辺ごとに計算していた（setdefault の引数評価）のを路線ごとに 1 回に | 提案パッチ |
| 本線チェーン | 連結成分ごとの全辺走査を始点ノード別の索引に置換 | 提案パッチ |
| 本線の切れ目 | 全端点の総当たりを KD-tree の近傍候補に限定（判定条件は同じ） | 提案パッチ |
| 施設へのランプ割当 | KD-tree で距離閾値内の施設だけを候補にする（同距離時の順序も同じ） | 提案パッチ |
| ランプ抽出 | 成分ごとの全辺走査を、その成分のノードの出辺に限定 | 提案パッチ |
| 区間生成 | ランプを路線で索引化 | 提案パッチ |
| 道路形状の切り出し | 座標の累積距離を再利用し、区間・公開データの切り出しを二分探索に（Shapely の substring と同じ結果） | 提案パッチ |
| 公開データの辺検索 | 道路上の位置からの辺検索を累積距離への二分探索に | 提案パッチ |
| 進捗・ログ | ramps / metrics の途中件数、段の開始、段の処理時間、中間成果物の保存時間を記録 | 提案パッチ |
| 出口ノードの統合 | 全候補の総当たり（O(n²)）を、最大閾値以内の組だけ KD-tree で列挙（i < j の昇順で同じ順に判定） | 追加 |
| 区間生成（チェーン上の施設） | チェーンごとの全施設・全ランプ走査を、出口ノード→施設とランプ端点→ランプの索引に（元の順序で処理） | 追加 |
| 本線の分断区間 | 上と同じ索引を使い、チェーン端点の座標を事前計算 | 追加 |
| 経路異常の判定 | 判定ごとに作っていたフィルタ付きグラフビュー（辺ごとに Python 関数を呼ぶ）を、本線だけの有向グラフ（1 回だけ作成）とグラフ全体に置換 | 追加 |
| 表示用レイヤー | 20〜100 m ごとの pandas の行アクセスを NumPy 配列に置換（NaN を除く平均・最大は pandas と同じ値） | 追加 |

## 検証結果（このリポジトリで実施）

**出力の同一性**：変更前のコード（`add-road-mri` の先頭）と変更後のコードで、同梱 fixture（栃木・米国 Ann Arbor・合成）の
全パイプラインを実行し、facility・ramp・ramp_way_map・section・section_distance・sample_point・display_feature・
quality_flag・classification_feature・facility_osm_map の全行・全列（run_id を除く）を比較した。3 地域ともすべて一致。
大規模化した合成ネットワーク（下記 ×40）でも、施設・ランプ・区間・距離・異常フラグのダイジェストが一致した。

**大規模化の測定**：合成ネットワーク（典型形状 8 施設）を経度方向に並べて複製し、段ごとの処理時間を測った（秒、4 vCPU の
クラウド環境。一部の測定は別の処理と並行したため ±30 % 程度ばらつく。例：metrics は同条件で 31〜46 秒）。
×80 でも変更前と変更後の出力ダイジェストは一致した。

| 段 | 変更前 ×40（320 施設） | 変更後 ×40 | 変更前 ×80（640 施設） | 変更後 ×80 |
| --- | ---: | ---: | ---: | ---: |
| network | 1.36 | 2.03 | 2.87 | 2.91 |
| facilities | 1.09 | 0.68 | 3.75 | 0.71 |
| ramps | **24.08** | **0.52** | **136.74** | **1.02** |
| sections | 0.52 | 0.24 | 1.98 | 0.35 |
| metrics（DEM・曲率・勾配） | 30.71 | 46.48 | 63.91 | 64.00 |
| classify + quality | 2.73 | 2.79 | 5.47 | 4.92 |
| 表示用レイヤー | 24.30 | 7.84 | 79.56 | 14.93 |

変更前は ramps・facilities・sections が施設数の 2 乗以上で伸びる（施設 2 倍で ramps は 5.7 倍）。変更後はすべての段が
施設数にほぼ比例する。California（4,037 施設、×80 の約 6 倍）規模では、変更前の ramps は 1 時間を超え（2 乗則で約 90 分）、
変更後は数秒と見込まれる（提案者の実測 8.92 秒と整合）。

**提案者の測定（California、提案者の PC）**：同一入力の先頭 3 施設・10 ランプのランプ抽出が 5.72 秒 → 0.0054 秒で、
全 dataclass 属性・辺属性・座標が一致。全 4,037 施設・20,758 ランプの抽出が 8.92 秒。全工程の所要時間と、区間生成以降の完了は未確認。

**テスト**：ruff・mypy（src 86 ファイル）・pytest（`tests/unit/test_network_optimization.py` に、道路切り出しと Shapely の一致、
辺検索の境界、切れ目検出、方位の計算回数、出口ノード統合と総当たり実装の一致〈乱数 5 通り〉、索引付き区間生成と全走査の一致、
NaN 統計と pandas の一致を追加）。

## 未確認・残課題

- California など州全域での全工程の完了時間（本環境から Geofabrik に接続できないため未測定）。
- metrics 段（DEM 標本化・曲率・勾配）は要素数に比例し、本測定で最も時間がかかる段。州全域では DEM タイルの取得時間も加わる。
- 経路異常の判定（gap_sections）は分断のある組ごとにグラフ探索する。分断が多い地域では時間がかかりうる（本測定では分断なし）。

## 再現

```bash
uv run ruff check src tests scripts
uv run mypy
uv run pytest -m "not network"
uv run roadmri build --range tochigi_small,us_annarbor_small --offline
```

ランプ抽出の変更前後比較（同じ facilities 段の中間成果物を使う）：変更前コミットのソースを `data/optimization-baseline/` に展開してから実行する。

```bash
git archive --format=tar --prefix=optimization-baseline/ <変更前コミット> src | tar -x -C data
uv run python scripts/benchmark_network.py --range california --limit 3
```

`--limit 0` は全施設で旧処理も実行するため長時間かかる。`data/logs/roadmri.jsonl` の `step.seconds` が段の処理時間、
`checkpoint.seconds` が中間成果物の保存時間。

大規模地域の build を途中から再開する場合（例：ランプ段まで保存済み）：

```bash
uv run roadmri build --range california --from-step sections
```
